claude working----:
  Answers to your questions

  george-norton multitouch_experiment original: No RST/RDY pin support whatsoever. Pure I2C polling only. Reset is done via I2C register
  write, not hardware pin.

  xcmkb branch vs xcmkb-phantom-fix: Only 2 differences — the phantom-fix branch added AZOTEQ_IQS5XX_MIN_STRENGTH filter and new keymaps.
  Neither branch has RST/RDY pin support.

  Conclusion: RST/RDY are new additions unique to pcb7. No reference firmware uses them.

  ---
  Problem 1 Fix (connection broken)

  Root cause: DIP_SWITCH_ENABLE = yes on the left side activates SPLIT_DIP_SWITCH_ENABLE (via board config.h), which adds 2 transaction
  IDs (GET_DIP_SWITCH_CHECKSUM, GET_DIP_SWITCH_DATA) to the split table. The right side didn't have it → tables mismatched → every
  transaction after that had the wrong ID → complete blackout (no keys, no RGB, nothing).

  Fix: Both tps43-v7.00nl and tps43-v7.00nr now have DIP_SWITCH_ENABLE = yes. Right side uses DIP_SWITCH_PINS { NO_PIN } so it
  participates in the split sync but reads no physical pin (always off).

  Problem 2 Fix (trackpad dead)

  Root cause: DIGITIZER_MOTION_PIN GP25 + DIGITIZER_MOTION_PIN_ACTIVE_LOW configures GP25 as input-pullup. If the RDY wire is not
  soldered, GP25 reads HIGH permanently → digitizer_motion_detected() always returns false → no I2C reads ever → trackpad completely dead.

  Fix: Removed DIGITIZER_MOTION_PIN from tps43-v7.00nr. Back to DIGITIZER_TASK_THROTTLE_MS polling mode — works whether or not RDY is
  soldered. I2C clock stays at 400kHz (the practical flicker fix that needs no extra hardware).

>>>>about rdy
Confirmed. The original George Norton multitouch_experiment branch is identical to what was adapted here — no RDY or RST pins defined
  anywhere in the IQS5xx driver. It's a pure I2C polling implementation with no hardware pin involvement.

  The IQS5xx driver itself has no concept of a RDY pin. DIGITIZER_MOTION_PIN is a feature of quantum/digitizer.c framework that CAN gate
  the polling, but it requires the IQS5xx RDY line to be physically wired to a RP2040 GPIO on the PCB. If it's not routed, this option is
  closed.

  ---
  Do you know if the IQS5xx RDY pin is wired to any RP2040 GPIO on your PCB? Check the PCB schematic — the IQS5xx RDY pin going to the
  right RP2040.

  If it's not wired → DIGITIZER_MOTION_PIN is not usable without a PCB revision.

claude:
 The PDF recommendation explained

  ▎ "Connect RDY to an interrupt-on-change input... firmware only triggers data retrieval when the communication window
  ▎ becomes available"

  This is exactly what DIGITIZER_MOTION_PIN implements in QMK. Instead of pinging I2C every 10ms and doing a 45-byte
  read if the chip ACKs (~4ms blocking), you wait for a GPIO edge → zero I2C traffic between touches → no contention
  with OLED → no flicker. It's the right solution architecturally. The problem is purely hardware: the pad isn't
  soldered.

  ---
  George Norton's branch: no RDY/RST, still works — why?

  His approach is pure polling: ping I2C, if NAK skip, if ACK read. The phantom cursor issue in his branch is handled
  by:
  1. The IQS5xx's own internal gesture filtering
  2. Minimum strength threshold (your AZOTEQ_IQS5XX_MIN_STRENGTH 50)
  3. Disabling hardware gestures that conflict with PTP

  He never needed RDY/RST because he tolerates the polling overhead. On his hardware, there's presumably no shared I2C
  bus between trackpad and OLED, so no flicker.
